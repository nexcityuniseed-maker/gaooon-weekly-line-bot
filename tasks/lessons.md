# 教訓 (lessons)

## 2026-06-01 月境界で先週データが0件になる（当月固定バグ）

### 症状
- 6/1(月)の定期配信で全5店が「低評価アンケート0件・Googleクチコミ0件」。
- ログに `WARN: filter toggle all-failed / methods=['standard', 'force=Timeout', 'js=js_no_target']`。
- 5/28(木)の手動runでは正常にデータ取得できていた（11/2/20/5/16件）。

### 根本原因
- GaoooN のアンケート結果ページは年/月セレクタが **初期表示=当月固定**。
- コードは常に `TODAY.month`（当月）を選んでいた。
- 週次レポートの対象は「先週月〜日」。月初の月曜（例: 6/1）は対象週(5/25〜5/31)が**前月(5月)**にあるのに、コードは**6月**を見ていた → 6月はデータほぼ無し → 0件。
- 「満足度フィルタのトグル失敗(all-failed)」も「Googleクチコミ0件」も、**すべて『見ている月が空』という1つの原因の下流症状**だった。フィルタ要素やクリック手段の問題ではなかった。

### なぜ気づきにくかったか
- テストはすべて5月中（5/26〜5/28）に実施。その間は「当月=対象週の月」が偶然一致していて動いていた。
- 月境界をまたぐ初めての実行が6/1で、そこで初めて露見した。
- 直前の数コミット（force-click / jsフォールバック / 月再トグル / UA偽装）は**下流症状（トグル失敗）を叩いていた**ため効かなかった。

### 修正
- `months_in_range(start, end)`: 対象週がまたぐ (年,月) を算出（同月=1要素、月境界週=2要素）。`REPORT_MONTHS` として保持。
- フロー順序を是正：**①対象年月を選択 → ②データが載った状態でフィルタをトグル → ③parse**。
  （旧コードは「フィルタ→月」の順で、空の当月でトグルして失敗していた）
- `_select_year_month()` は「別月→対象月」のガチャ操作でBubbleの非同期再描画を確実に誘発（クラウド初期化対策を兼ねる）。
- `collect_for_store` は `REPORT_MONTHS` をループし、timestampで重複除去。

### 一般化できる教訓
1. **「当月/今日」を使う箇所は、対象が前月/前週に落ちるケースを必ず疑う。** 集計の「対象期間」と「UIフィルタが指す期間」を取り違えない。日付境界（月初・年初・週またぎ）はテストケースに必須。
2. **症状（クリック失敗・タイムアウト）を直接叩く前に、上流（そもそも表示すべきデータが来ているか）を確認する。** スクショ等の証拠で「どの層で壊れているか」を特定してから修正する。
3. **「成功していた過去run」と「失敗run」のログ差分を取る**のが最速の原因特定。今回は `month re-toggled 4月→5月`（成功）と `5月→6月`（失敗）の差が決定打だった。

## 2026-06-01 cron遅延 × 手動送信による二重配信

### 症状
6/1の定期配信(cron)が11:00に発火せず、修正のため手動で配信（12:54・14:33）。
ところが**cronが約5時間遅れて15:53 JSTに発火**し、15:58に3通目が届いた（重複）。

### 原因
- GitHub Actionsのcronは高負荷時に大幅遅延・最悪ドロップする（毎時00分は特に混雑）。
  今回は約5時間遅れて発火。cronは自動で `send` モードなので配信される。
- 遅延中に手動送信したため、後から発火したcronと重複した。
- 幸い発火時点でmainに修正がマージ済みだったので内容は正しかったが、重複は重複。

### 対策（実装済み）
- **対象週(先週月曜)をキーにした二重送信ガード**を追加。
  - `already_sent_this_week()` / `record_sent_this_week()`、マーカー `.last_sent.json`。
  - 送信成功時に対象週を記録。同じ週の2回目以降は `SEND_MODE=send` でもスキップ。
  - `FORCE_SEND=1` で意図的な再送は可能（修正版の差し替え配信などに使う）。
  - ローカルはファイル、GitHub Actionsは `actions/cache`（週キー）で永続化。

### 教訓
- **「自動送信される定期ジョブ」がある日に手動で同じ送信をすると重複する。**
  遅延ジョブは後から来る。手動送信するなら(a)その週のcronを無効化する、
  (b)冪等ガードを入れる、のどちらかを先に。今回は(b)を実装。
- 配信・課金・通知など**外部副作用のある定期処理には、対象期間キーの冪等性**を最初から持たせる。

## 2026-06-22 LINE月間メッセージ上限で配信が落ちる → 1通集約で対応

### 症状
6/15の定期配信が1/5店しか届かず、2店目以降が `HTTP 429: You have reached your monthly limit.`。

### 原因
- LINE Messaging APIは**送信操作回数ではなく「届いた相手の人数」で課金**する。
  グループ送信は参加者全員に配信され、**1 push = グループ人数分**カウントされる。
- 対象グループは10人。店舗ごとに1 push（週5 push）→ 5×10=50通/週 → 約200通/月。
- 無料(Communication)プランは**月200通**。通常運用でも月末に上限へ達する構造で、
  6/1のデバッグ重複配信（+10 push≈+100通）で月半ばに枯渇した。

### 対応（実装済み）
- **全5店を1通(1カルーセル)に集約**（目次バブル＋各店2カード＝11バブル、上限12以内）。
  `build_combined_flex_message()` / `build_store_cards()`。送信は週5 push→**1 push**に削減
  （50通→10通/週、月約40通）。情報量は従来の店舗別カルーセル相当を維持。
- 明細描画は `_survey_alert_items / _review_alert_items / _improvement_items / _good_items`
  に切り出して再利用。

### 教訓
- **LINE pushの課金単位は「メッセージオブジェクト×受信者数」**。1リクエストに複数
  メッセージを束ねても各メッセージが個別課金されるので、**メッセージ数自体を減らす
  （カルーセルに集約）**のが正解。通数設計は「店舗数×グループ人数×頻度」で見積もる。
- 配信量はクォータ(`/v2/bot/message/quota`,`/consumption`)とグループ人数
  (`/v2/bot/group/{id}/members/count`)で実測できる。

## 2026-06-22 1通集約版が「カルーセル50KB上限」超過で送信失敗（HTTP400）

### 症状
全5店を1通に集約後、定期配信が `HTTP 400 Too large flex message. The maximum size of
JSON data that defines a carousel is 50 KB.` で失敗（exit 6、データ取得は全店成功）。

### 原因
- LINEのFlexカルーセルはJSONサイズ**50KB上限**。
- 5店×2カード（特にアンケート低評価のスコア●行が冗長）＝約**69.7KB**で超過。
- データ量は週で変動するため、固定の詳細度では重い週に超過し得る。
- 注意：1 pushに複数メッセージを束ねても各メッセージが個別課金なので、消費削減には
  「1メッセージ(1カルーセル)化」が必須。その1カルーセルが50KB上限に縛られる。

### 対応（実装済み）
- `build_combined_flex_message()` に**サイズ自動調整**を実装。詳細度レベルを段階的に
  下げ（survey 4→1、スコア●→1行圧縮、review/improve/good を削減）、カルーセルJSONが
  48KB（安全マージン）以内になる最も詳しいレベルを採用。
- `build_store_cards()` に `survey_limit/show_dots/review_limit/improve_limit/good_limit`、
  `_survey_alert_items()` に `show_dots` を追加。
- 検証：実データで Lv2（42.9KB）採用、重い合成データでも Lv3（46.5KB）で50KB以内。

### 教訓
- **Flexカルーセルは50KB上限**。多件数を1通に集約するなら、サイズ実測＋動的トリムで
  上限内に収める設計を最初から入れる（固定レイアウトは重い週に破綻する）。
- 送信前にJSONバイト数を測る癖をつける（`json.dumps(...,separators=(",",":"))` のUTF-8長）。

### 既知の残課題（フォロー候補）
- **年セレクタ**: `select_option(label="YYYY年")` が TimeoutError（当年=2026がデフォルト選択済みのため現状は実害なし、best-effort・6sでfail-fast化済み）。**1月の年境界週（先週が前年12月）でのみ問題**になり得る。要・1月での実地検証。
- altText の「要注意 N件」とKPIバッジの件数が異なる場合がある（別集計・既存仕様、本バグとは無関係）。
